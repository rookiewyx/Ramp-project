# 压测与链路追踪记录

审核服务（模块三）上线前的压测。目的不是跑出一个好看的 QPS，而是回答三个问题：
**能扛多少、时间花在哪、出问题时怎么坏。** 每轮都看链路追踪找原因，修完再测。

## 怎么测

| 项目 | 设置 |
|---|---|
| 机器 | 云端开发容器，**2 个 vCPU**；压测工具、接口、worker、模拟模型、数据库都挤在这两个核上，绝对数字偏保守 |
| 负载 | locust 闭环：108 个“员工”每 5 秒提交一笔并等到出结论；12 个“财务”刷待办、做复核。目标到达速率约 **20 笔/秒（7.2 万笔/小时）** |
| 数据 | 合成报销 300 笔：文字版 PDF 69%，拍照件 28%，无附件 3%，和真实比例一致 |
| 模型 | `scripts/mock_models.py` 模拟：视觉模型中位数 3.5 s（实测 qwen3-vl-plus 的均值），文本模型 1.2 s，对数正态长尾。可以模拟服务方并发配额（超出返回 429） |
| 链路 | OpenTelemetry，API → Redis 队列 → worker → 模型调用 → SQL 是同一条链路；`OTEL_EXPORTER=file` 写 JSONL，`scripts/trace_report.py` 汇总各环节 P50 / P95 |

为什么不直接打百炼：要测的是**我们的系统**能扛多少。打真实接口会花钱、被限流，模型延迟的波动也会盖住系统本身的瓶颈。模拟延迟取自实测值。

## 结果一览

端到端：员工提交 → 拿到审核结论。吞吐：每秒完成审核的笔数。

| # | 配置 | 吞吐 | 端到端 P50 | 端到端 P95 | 说明 |
|---|---|---|---|---|---|
| E0 | 默认配置（任务限速 60/m，8 并发） | 0.96/s | 17.8 s | 23.9 s | 吞吐被限速卡死在 1 笔/秒，时间全花在排队 |
| E1 | 去掉任务限速 | 2.07/s | 0.12 s | 5.1 s | 到达多少处理多少（这轮负载较轻） |
| E5 | 32 并发，SQLite，20 笔/秒 | **20.5/s** | **0.11 s** | **5.0 s** | 文字版 PDF P50 67 ms、拍照件 P50 3.6 s |
| E5' | 同上，PostgreSQL | 20.5/s | 0.16 s | 5.2 s | 这个量级下数据库不是瓶颈 |
| E6 | 8 并发，20 笔/秒 | 6.9/s | 13.8 s | 19.6 s | 并发不够，排队时间占 94% |
| E7 | 模型配额 10，worker 32 并发 | 11.0/s* | 0.11 s | **40.7 s** | 85% 的模型请求被 429 拒绝；58 笔重试用尽后降级成“识别失败” |
| E8 | 配额 10，调用方限并发（视觉 8 + 文本 2） | 7.8/s | 10.4 s | 26.2 s | 不再被拒、零失败，但拍照件占满线程，文字版 PDF 也跟着排队 9.6 s |
| E9 | 配额 10，拍照件单独队列 | 8.5/s | **0.08 s** | 40.2 s | 文字版 PDF 恢复到 P50 52 ms；拍照件受配额限制排队 |
| E10 | 最终配置，配额充足，20 笔/秒 | **20.3/s** | 0.19 s | 5.8 s | 文字版 PDF P50 80 ms，拍照件 P50 4.3 s，零失败 |

\* E7 的吞吐里包含了 58 笔降级成“识别失败、转人工”的单子，是虚高的。

E0–E3 的链路数据受下文问题 2 影响，排队时间的 P99 偏大；但吞吐和端到端是 locust 在客户端测的，不受影响。

## 发现并修复的问题

### 1. 默认的任务限速把吞吐卡在 1 笔/秒（E0）

`TASK_RATE_LIMIT=60/m` 本意是保护模型接口，但 Celery 的限速是按**任务**算的：不需要调模型的文字版 PDF 也被限住。
链路显示排队 P50 17.5 秒、worker 处理只要 11 毫秒。

**修复**：默认不限速。保护模型接口改成在模型调用处限制并发（见问题 4）。

### 2. 链路“串号”：约 8% 的请求被挂到了别人的链路下面

压测时发现一条链路里出现了 5 笔不同报销的审核。追下去：

- 同一个长连接上，客户端发得快时，uvicorn 会在**上一个请求发送响应的过程中**就为下一个请求创建任务。新任务复制了当时的上下文，于是挂到了上一个请求的链路下面。
- 原来的 `@app.middleware("http")`（BaseHTTPMiddleware）在另一个任务里读请求体，让问题更明显。

**修复**：
- 请求 ID 改用纯 ASGI 中间件；
- 最外层加一个 `FreshTraceContext`，每个请求从空的链路上下文开始。请求头里带了 `traceparent` 的，仍会接上上游链路；
- 不再记录 `http receive` / `http send` 这类小 span。

修复后 API 进程里不再出现挂错父节点的请求 span。

### 3. 链路里一条 SQL 都没有

官方的 `opentelemetry-instrumentation-sqlalchemy` 只支持 SQLAlchemy < 2.1，装了 2.1 时只打一行警告就**静默跳过**。

**修复**：直接挂 SQLAlchemy 的游标事件，自己产出 SQL span。只记录带占位符的语句，不记录参数值，因为参数里可能有员工填写的内容。有单元测试覆盖。

### 4. 模型配额不够时，重试风暴让情况更糟（E7）

worker 32 并发，模型服务配额只有 10：

- 2317 次请求被拒，只有 406 次成功；
- 客户端重试、任务重试层层叠加，端到端 P95 从 5 秒涨到 41 秒；
- 58 笔拍照件重试用尽，被降级成“识别失败、转人工”，平白多给财务添了活。

**修复**：在调用方排队，而不是打过去等着被拒。`VLM_MAX_CONCURRENCY` / `LLM_MAX_CONCURRENCY` 限制每个进程同时在途的模型请求，等待时间记在链路的 `model.wait_ms` 上。

E8 的结果：零拒绝、零失败。

### 5. 拍照件排队时，秒级就能审完的单子也被拖住（E8）

限了模型并发以后，拍照件在等名额，但它们占着 worker 线程。32 个线程全被等视觉模型的任务占满，文字版 PDF 也要排 9.6 秒。

**修复**：舱壁隔离。拍照件进 `vlm` 队列，文字版 PDF 和无附件的进 `default` 队列，分开起 worker。`vlm` 那组的并发按视觉模型配额设置。

E9 的结果：同样的配额下，文字版 PDF 的端到端 P50 从 9.6 秒回到 52 毫秒。

### 6. 提交接口写成了 async def，里面却全是同步调用

数据库、文件、Redis 都是同步调用，写在 `async def` 里会堵住事件循环，所有查询请求都得排在它后面。

**修复**：改成普通 `def`，交给线程池执行。

查询接口 P95 从 250 ms 降到 91 ms（E5 → E10）。提交接口 P95 反而从 163 ms 升到 302 ms：E10 多开了一个 worker 进程，2 个核上 CPU 争用更重，这一项需要在更多核的机器上复测。

## 容量怎么估

worker 处理一笔的平均时间约 1.15 秒，其中 91% 花在视觉模型上。按利特尔法则：

> **吞吐上限 ≈ 并发数 ÷ 平均处理时间**

E6 是 8 并发，算出来 8 ÷ 1.15 ≈ 7.0 笔/秒，实测 6.9 笔/秒。

拍照件单独看：吞吐上限 ≈ 视觉模型并发配额 ÷ 3.6 秒。配额 10 时约 2.8 张/秒，按拍照件占 28% 折算，总量约 10 笔/秒。

所以**瓶颈在模型配额，不在我们的服务**：

- 数据库：SQL P99 ≤ 12 ms；
- 排队：配额充足时 P95 ≤ 12 ms；
- 规则引擎：P50 3 ms。

要扛更多，按收益排序：

1. 提高视觉模型配额，或自建视觉模型（AutoDL 上的 vLLM）；
2. 继续减少走视觉模型的比例，分级识别已经让 72% 的发票不调模型；
3. 加 worker。只有在配额充足时才有用。

## 局限

- 2 个 vCPU 上所有组件互相抢 CPU，提交接口的 P95 偏高，换到更多核的机器上会好很多。
- 模型是模拟的：真实服务的延迟分布、限流方式可能不同，上线前要用真实接口小流量复测。
- 业务库用的是 SQLite 和 PostgreSQL，docker compose 里配的是 MySQL，没有单独压测 MySQL。

## 在自己电脑上复现

```powershell
# 1. 模拟模型（另开窗口）
.venv\Scripts\python scripts\mock_models.py --port 8009

# 2. 环境变量：模型指向模拟服务，链路写文件
$env:LLM_BASE_URL="http://127.0.0.1:8009/v1"; $env:VLM_BASE_URL="http://127.0.0.1:8009/v1"
$env:LLM_API_KEY="x"; $env:OTEL_ENABLED="true"; $env:OTEL_EXPORTER="file"

# 3. 接口和两组 worker（各开一个窗口，每个窗口都要先设好上面的环境变量）
docker compose up -d redis
.venv\Scripts\python -m ramp_agent.service api
.venv\Scripts\python -m ramp_agent.service worker --queues default --concurrency 16
.venv\Scripts\python -m ramp_agent.service worker --queues vlm --concurrency 24

# 4. 压测 3 分钟，然后看链路
.venv\Scripts\locust -f tests\load\locustfile.py --host http://127.0.0.1:8080 --headless -u 120 -r 10 -t 3m --csv reports\load\run1
.venv\Scripts\python scripts\trace_report.py reports\traces.jsonl
```

想在 Jaeger 里看单条链路：`docker compose up -d jaeger`，把 `OTEL_EXPORTER` 改成 `otlp`，打开 http://127.0.0.1:16686。
